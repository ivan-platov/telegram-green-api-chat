# Telegram-чат через GREEN-API

React-клиент личных текстовых переписок в Telegram через GREEN-API. Пользователь подключает свой инстанс, открывает чат по номеру телефона, отправляет текст и получает ответы через HTTP-очередь уведомлений. Визуальный ориентир — MAX Web; источник локального фона указан в [описании ассета](src/assets/README.md).

Поддерживаются несколько личных диалогов, сохранение доступа, истории и черновиков, статусы сообщений и виртуализация обоих списков. Группы, медиа, звонки, поиск, редактирование, удаление и автоматический импорт всех Telegram-диалогов не входят в объём проекта.

## Запуск

Требуется Node.js **24 или новее**. Проверено на Windows с Node 24.16.0/npm 11.13.0.

```powershell
git clone https://github.com/ivan-platov/telegram-green-api-chat.git
cd telegram-green-api-chat
npm ci
npm run dev
```

Откройте [локальный чат](http://127.0.0.1:5178/). Если PowerShell блокирует npm.ps1, используйте `npm.cmd`/`npx.cmd`. Перед `npm ci` остановите dev-сервер: Windows может удерживать нативный модуль сборщика.

Для проверки готовой сборки:

```powershell
npm run build
npm run preview
```

Адрес preview отображается в терминале. Backend не нужен. API URL по умолчанию задаётся через `VITE_GREEN_API_URL` или исходное значение в клиенте; его можно изменить на экране подключения. Токен в VITE-переменные не помещать: они попадают в публичную сборку.

## Как пользоваться

1. Авторизуйте Telegram-инстанс в [кабинете GREEN-API](https://console.green-api.com/). Нужен готовый инстанс, не Bot API-токен.
2. Введите адрес API, ID инстанса и токен. Доступ сохраняется в этом браузере, восстановление автоматически проверяет владельца аккаунта.
3. Нажмите **«Новый чат»**. В основной области появится карточка телефона; введите международный номер и нажмите **«Начать чат»**. Открытие диалога ничего не отправляет.
4. Собеседник появится слева. Повторное открытие того же chatId выбирает существующую переписку без дубля.
5. Введите текст и отправьте кнопкой. При fine pointer/hover и отсутствии touch points Enter отправляет, Shift+Enter добавляет перенос. На touch/hybrid Enter добавляет перенос.
6. На узком экране список и переписка — отдельные панели с кнопкой возврата.

Находить аккаунт по телефону можно только в пределах возможностей CheckAccount и приватности Telegram. Номер не вычисляется из chatId. Для реальной приёмки нужны два разных аккаунта: переписка с самим собой не доказывает получение ответа другого пользователя.

## Что сохраняется

- **localStorage:** адрес API, ID/токен и проверенные метаданные подключения. Сохранение относится к конкретному origin и профилю браузера. Токен хранится без дополнительного шифрования.
- **IndexedDB:** реестр открытых диалогов, сообщения и локальные попытки отправки, черновики по чатам, свидетельства статусов, выбранный диалог и бюджеты сверок. Workspace разделён по API URL, инстансу и владельцу Telegram-аккаунта.
- Позиции чтения сохраняются между переключениями в текущем окне. После полного reload восстанавливаются данные и конец переписки; сохранение позиции чтения между запусками не заявляется.

Слева находятся **открытые в этом приложении личные диалоги**. GetChats существует у провайдера, но автоматический импорт всех переписок аккаунта не входит в выбранный объём.

После перехода со старой версии v1 адресата может потребоваться один раз открыть по номеру: старая запись lastChat не содержала владельца. Доступ мигрирует, кандидат не удаляется, но не приписывается аккаунту без основания. Для новых workspace диалоги/выбор/drafts восстанавливаются автоматически. История из сервиса дополняет локальные записи, не стирает их по отсутствию в ответе.

**«Отключиться»** сохраняет текущий draft, останавливает обмен и удаляет доступ до освобождения очереди. Локальная переписка остаётся. Эта кнопка не разлогинивает Telegram на стороне GREEN-API и не удаляет сообщения собеседника. При отказе хранилища успех не имитируется.

## История, статусы и связь

- GetChatHistory получает сначала 100 записей. При приближении к началу ленты автоматически увеличивается count на 100; постоянной кнопки загрузки нет. Offset/cursor не выдумываются. Малый ответ не объявляется концом всего Telegram-архива.
- Сообщения и список чатов виртуализированы через зафиксированный TanStack Virtual. Даты — отдельные display rows, высота сообщений измеряется. При чтении выше новые сообщения показывают индикатор, не тянут вниз.
- Время берётся из серверной записи либо локальной попытки, форматируется в зоне браузера. Отсутствующее время не выдумывается.
- Часы — отправляется; одна галочка — доставлено; две — прочитано; предупреждение — доставка не подтверждена; ошибка — подтверждённый отказ. Раскрытие подробностей доступно только у проблемных сообщений. HTTP 200/idMessage от SendMessage не означает доставку.
- Поле ввода очищается при отправке, без ожидания API. Следующий черновик не затирается ответом предыдущего запроса. Если локальную попытку не удалось сохранить и отправка не началась, исходный текст возвращается в поле.
- Пропущенные подтверждения сверяются через GetMessage с ограниченным сохраняемым бюджетом. Повторная отправка текста автоматически не выполняется.
- Входящие и исходящие с API/другого клиента обрабатываются последовательно; релевантное событие сохраняется до DeleteNotification. Ошибка сохранения останавливает ACK.
- Web Locks допускает одного владельца API-очереди среди вкладок одного origin. Ожидающая вкладка не вызывает API и не меняет drafts. Кабинет GREEN-API, другой origin/профиль или внешняя интеграция этой блокировке не подчиняются.
- Состояние/настройки/владелец проверяются периодически; временные ошибки не сбрасывают рабочую переписку в форму логина. Настройки сервиса автоматически не меняются.
- Документированное уведомление `quotaExceeded` сохраняется до ACK и показывается отдельно. Оно не блокирует всю очередь. Ошибки ручной сверки статуса показываются у сообщения; проверку можно повторить без повторной отправки текста.

Для HTTP-получения включите входящие уведомления и оставьте Webhook URL пустым. Для событий исходящих/статусов нужны соответствующие outgoing-флаги. При проблемах приложение показывает действие и подробности. Без Web Locks безопасный обмен выключен.

## Проверки

```powershell
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

Браузерные тесты используют вымышленные данные, перехватывают внешние запросы и поднимают собственный dev-сервер на **5188**, не используют реальный токен. IndexedDB, Web Locks и геометрия проверяются в настоящем Chromium. Отчёты, traces и снимки создаются в игнорируемой `.artifacts/`; её содержимое не требуется для запуска проекта.

После build отдельно проверьте production:

```powershell
npm run test:e2e:production
```

Команда поднимает preview на **5189** и проверяет обмен, сохранение, сверку статусов и ошибки на fixture API. Это не доказательство работы настоящего сервиса. Пределы проверки: Chromium на Windows, включая узкие viewport и эмуляцию touch; нативная IME, физическая экранная клавиатура, скринридеры и другие браузеры не объявляются проверенными. Новый реальный двусторонний обмен после последнего ревью не выполнялся.

Токен вводится только в интерфейсе. Приватные материалы, реальные env-файлы, node_modules, dist и тестовые артефакты исключены из Git. Dev-сервер запрещает выдачу приватных файлов. Сохранённый в браузере токен доступен JavaScript того же origin; используйте доверенный профиль и не подключайте сторонние скрипты.

## Методы GREEN-API

Используется Telegram API, не Telegram Bot API и не прямой MTProto. Базовый URL берётся из кабинета пользователя. Пути имеют вид `{apiUrl}/waInstance{idInstance}/{method}/{apiTokenInstance}`; действительные реквизиты в репозитории отсутствуют.

| Метод               | Назначение                                | Официальная документация                                                                               |
| ------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| GetStateInstance    | Проверка состояния инстанса               | [Контракт](https://green-api.com/telegram/docs/api/account/GetStateInstance/)                          |
| GetSettings         | Настройки уведомлений                     | [Контракт](https://green-api.com/telegram/docs/api/account/GetSettings/)                               |
| GetAccountSettings  | Идентификатор владельца Telegram-аккаунта | [Контракт](https://green-api.com/telegram/docs/api/account/GetAccountSettings/)                        |
| CheckAccount        | Разрешение номера телефона в chatId       | [Контракт](https://green-api.com/telegram/docs/api/service/CheckAccount/)                              |
| SendMessage         | Отправка `{chatId, message}`              | [Контракт](https://green-api.com/telegram/docs/api/sending/SendMessage/)                               |
| ReceiveNotification | Последовательное получение уведомлений    | [Контракт](https://green-api.com/telegram/docs/api/receiving/technology-http-api/ReceiveNotification/) |
| DeleteNotification  | Подтверждение обработанного receiptId     | [Контракт](https://green-api.com/telegram/docs/api/receiving/technology-http-api/DeleteNotification/)  |
| GetChatHistory      | Получение истории по chatId и count       | [Контракт](https://green-api.com/telegram/docs/api/journals/GetChatHistory/)                           |
| GetMessage          | Сверка одного исходящего сообщения        | [Контракт](https://green-api.com/telegram/docs/api/journals/GetMessage/)                               |

Для HTTP-очереди в кабинете нужны `webhookUrl: ""` и `incomingWebhook: "yes"`; для исходящих и статусов — `outgoingWebhook`, `outgoingAPIMessageWebhook`, `outgoingMessageWebhook` со значением `"yes"`. Приложение читает настройки, но не вызывает SetSettings автоматически. [Технология HTTP API](https://green-api.com/telegram/docs/api/receiving/technology-http-api/), [формат ограничения тарифа](https://green-api.com/telegram/docs/api/receiving/notifications-format/service/QuotaExceeded/).

## Структура исходников

`src/App.tsx` собирает экраны из `views/`; UI находится в `components/`, React-хуки — в `hooks/`.

- `types/` содержит только `type`, `interface` и type-only импорты. ESLint запрещает исполняемый код в этой папке.
- `services/` содержит правила обработки данных и побочные эффекты. `PhoneService` нормализует и подписывает номера, `MessageService` объединяет сообщения и связывает отправку с ответом API, `DeliveryService` обрабатывает статусы, `HistoryService` разбирает историю. Сервисы используют прямые импорты; отдельного слоя моделей нет.
- Все файлы в `services/` именуются в kebab-case: `delivery.service.ts`, `draft-controller.ts`, `history-loader.ts`, `chat-session.ts`. Имена классов остаются в PascalCase.
- `services/api/` использует Axios: отдельный клиент для подключения, общий базовый URL, JSON, `AbortSignal`, таймаут 20 секунд и преобразование ошибок в безопасный `ApiError`. Методы GREEN-API вызываются через `GreenApiService`. Планировщик чтения сохраняет ограничения частоты и объединение одинаковых запросов; отправка автоматически не повторяется. Ошибки Axios с конфигурацией и токеном не выходят за границу транспорта.
- `styles/tailwind.css` подключает Tailwind через Vite; размеры, расположение и состояния элементов задаются utility-классами в `className`. Prettier сортирует их. `styles/index.scss` содержит глобальные настройки и повторно используемые стили: формы, кнопки, ошибки, аватары, маски иконок и пустые состояния. Отдельный вход SCSS нужен потому, что Tailwind 4 не предназначен для обработки Sass.

Атрибуты `data-ui` используются для стабильных браузерных проверок геометрии, `data-status`, `data-kind` и `data-direction` — для состояний отображения. Изменение utility-классов не меняет тестовые селекторы.

Основания для транспорта и оформления: [Axios instance](https://axios-http.com/docs/instance), [настройки запросов](https://axios-http.com/docs/req_config), [отмена](https://axios-http.com/docs/cancellation), [ошибки](https://axios-http.com/docs/handling_errors), [Tailwind с Vite](https://tailwindcss.com/docs/installation/using-vite), [совместимость Tailwind и препроцессоров](https://tailwindcss.com/docs/compatibility), [SCSS в Vite](https://vite.dev/guide/features.html#css-pre-processors).

Компоненты не выполняют HTTP-запросы и не работают с IndexedDB напрямую. Сессия координирует обмен, а отдельные сервисы отвечают за отправку, очередь, историю и сверку статусов. Unit-тесты проверяют правила данных; браузерные тесты используют настоящее приложение и подменяют только внешний API.

## Правила отображения состояний

Тексты выводятся из состояния операции, а не из предположения о причине сбоя. Ошибка запроса не доказывает отсутствие интернета; авторизация инстанса не доказывает доставку сообщения. Положительный индикатор означает, что инстанс авторизован и последний запрос уведомлений завершился успешно. Подробности открываются нажатием на индикатор; предупреждения и действия также доступны в основной области.

`ConnectionService` задаёт общий приоритет индикатора и причины недоступности действий. Ошибки проверки подключения (`connectionError`) и получения уведомлений (`receiveError`) независимы: успешный запрос одного типа не очищает ошибку другого. Ошибки отдельных сообщений и истории остаются в своём контексте.

| Условие                                              | Что показываем / разрешаем                                                                                                                                             |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ошибка сохранения данных                             | «Данные не сохраняются». Отправка остановлена; текст остаётся в окне. Не обещаем, что черновик переживёт перезагрузку.                                                 |
| Ожидание Web Lock                                    | «Ожидаем доступ к чату». Обмен в этой вкладке ещё не запущен. Сам факт ожидания не выдаём за доказательство работы другой вкладки.                                     |
| Сессия завершилась ошибкой                           | «Подключение остановлено» и конкретная причина. Чтение локальной истории доступно; отправка недоступна.                                                                |
| Первичное подключение / восстановление               | «Проверяем подключение…» / «Восстанавливаем подключение…», ход операции и отмена. Повтор после ошибки содержит срок ожидания и не называется успешным восстановлением. |
| Проверка подключения завершилась ошибкой             | «Не удалось проверить подключение». Успешные запросы очереди эту ошибку не скрывают.                                                                                   |
| Инстанс `starting`                                   | «Инстанс запускается». Не называем это потерей интернета.                                                                                                              |
| `notAuthorized`, `pendingPassword`                   | Просим завершить авторизацию / двухфакторную авторизацию в кабинете GREEN-API.                                                                                         |
| `pendingCode`                                        | Совместимый текст для завершения авторизации, если такое значение уже пришло от сервиса.                                                                               |
| `blocked`                                            | «GREEN-API сообщает о блокировке инстанса».                                                                                                                            |
| `suspended`                                          | «На Telegram-аккаунте временные ограничения отправки». Не называем это полной блокировкой аккаунта.                                                                    |
| Неизвестное состояние инстанса                       | Сообщаем о неизвестном состоянии; не подставляем смысл известного статуса.                                                                                             |
| Входящие выключены или задан Webhook URL             | «Получение сообщений не настроено». Для HTTP-очереди нужны включённые входящие уведомления и пустой Webhook URL.                                                       |
| Первый запрос очереди ещё не завершился              | «Подключаем получение…». Положительный индикатор ещё не показывается.                                                                                                  |
| Временная ошибка очереди, есть автоматический повтор | «Повторяем запрос уведомлений…» и ошибка именно получения. Отправка временно недоступна.                                                                               |
| Получение остановлено                                | «Получение сообщений остановлено» и причина. Неизвестное/повреждённое уведомление не подтверждается как обработанное.                                                  |
| Получение не запущено                                | «Обмен сообщениями не запущен». Не обозначаем это общей «проблемой связи».                                                                                             |
| Настроены не все исходящие уведомления               | «Уведомления о доставке не настроены». Отправка допустима при работающем получении; сверка через GetMessage остаётся ограниченной.                                     |
| Не удалось записать реквизиты                        | «Доступ не сохранён в браузере». Это не ошибка сети и не ошибка сохранения истории; текущий обмен может продолжаться.                                                  |
| Все обязательные проверки успешны                    | «Получение сообщений работает». Не обещаем, что все сообщения доставлены или прочитаны.                                                                                |

При нескольких проблемах индикатор выбирает первую по этому приоритету; остальные остаются в подробностях. Проверка подключения показывает ход операции на кнопке и не скрывает уже известную ошибку до успешного результата. Историческое уведомление о лимите тарифа не выдаётся за доказательство текущей блокировки обмена.

| Операция / состояние                                                                                    | Правило текста и поведения                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Запрос отправки выполняется, серверного ID ещё нет                                                      | «Отправляется», часы. Это состояние локальной попытки.                                                                                                                                                                      |
| Получен ID, подтверждения доставки нет                                                                  | «Ожидаем подтверждения доставки», часы. Ответ SendMessage не считается доставкой.                                                                                                                                           |
| `delivered` / `read`                                                                                    | «Доставлено» / «Прочитано» только по уведомлению либо записи журнала для того же chatId и ID сообщения. Подтверждённое состояние не понижается более слабым ответом.                                                        |
| Подтверждённая ошибка отправки                                                                          | «Не отправлено», подробная причина. Ошибка без ID относится к чату и не привязывается к произвольному сообщению.                                                                                                            |
| Потерян ответ отправки, истекло время, повреждён ответ, не удалось сохранить ответ или исчерпана сверка | «Доставка не подтверждена». Не называем сообщение недоставленным и не повторяем автоматически. Предлагаем проверить переписку.                                                                                              |
| Отсутствует статус старого исходящего сообщения                                                         | Тот же нейтральный статус неизвестного результата; доступно раскрытие подробностей.                                                                                                                                         |
| Ручная сверка                                                                                           | «Проверяем статус…». Доступна только при рабочем подключении, получении и сохранении; запрос проверяет статус без повторной отправки текста.                                                                                |
| Ошибка сверки                                                                                           | Не меняет подтверждённые доставку/прочтение на ошибку отправки. Отображается как ошибка проверки, а не факт недоставки.                                                                                                     |
| Время сообщения                                                                                         | Серверное время имеет приоритет; подсказка различает серверное, локальное и старое сохранённое время. При конфликте серверных значений показывается первое с пояснением; отсутствующее время не выдумывается.               |
| История загружается                                                                                     | «Загружаем историю…» / «Загружаем сообщения…». Уже загруженные сообщения остаются видны.                                                                                                                                    |
| История ещё не запрашивалась                                                                            | «История ещё не загружена», а не пустой чат. В ожидающей вкладке объясняется необходимость активного подключения для загрузки.                                                                                              |
| История завершилась ошибкой                                                                             | «История не загружена» / «Не удалось загрузить историю», причина и повтор. Ошибка не трактуется как пустая история.                                                                                                         |
| Загруженная часть не содержит текста                                                                    | «Нет доступных текстовых сообщений» с пояснением, что речь о загруженной части ответа GREEN-API. Это не утверждение об отсутствии всей переписки в Telegram.                                                                |
| Открытие чата                                                                                           | «Открываем чат…». Невозможность разрешить номер не объявляется доказательством отсутствия аккаунта: учитывается приватность. При недоступности операции показывается причина.                                               |
| Черновик                                                                                                | «Сохраняем черновик…» только пока есть незавершённые записи; ошибка сохранения заменяет обещание сохранности предупреждением не закрывать вкладку.                                                                          |
| Кнопка отправки недоступна                                                                              | Видимая причина для сбоя подключения, сохранения, ожидания очереди или другой отправки. Пустой/слишком длинный текст объясняется подсказкой кнопки. Условия UI и команды отправки используют одну функцию.                  |
| HTTP 401/403, 429, другие ошибки                                                                        | Указываем отсутствие доступа, ограничение частоты или код отклонённого запроса соответственно. Не приписываем HTTP 469 недокументированное значение. Ошибки отправки с неопределённым результатом остаются неопределёнными. |

Основания значений API: [GetStateInstance](https://green-api.com/telegram/docs/api/account/GetStateInstance/), [OutgoingMessageStatus](https://green-api.com/telegram/docs/api/receiving/notifications-format/statuses/OutgoingMessageStatus/), [GetChatHistory](https://green-api.com/telegram/docs/api/journals/GetChatHistory/), [GetSettings](https://green-api.com/telegram/docs/api/account/GetSettings/), [стандартные ошибки](https://green-api.com/telegram/docs/api/common-errors/). Остальные строки описывают локальные правила приложения, а не дополнительные статусы GREEN-API.

Если удаление реквизитов не завершилось, показывается «Не удалось удалить сохранённый доступ». Это не объявляется ошибкой сохранения истории; успешное удаление не подтверждается. Если удалению помешал несохранённый черновик, отдельно остаётся его настоящая ошибка сохранения.

## Качество кода

Базовый профиль применяется к JavaScript, TypeScript и TSX, тестам и конфигурации. Версии зависимостей закреплены; используется поддерживаемый ESLint 10 с совместимыми React-плагинами. Предупреждения тоже завершают проверку ошибкой.

| Область        | Что проверяется                                                                                                                                                                                                                                        |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| JavaScript     | Рекомендуемые правила ESLint, неиспользуемые переменные, недостижимый код, debugger, const вместо var, строгое сравнение (кроме намеренного сравнения с null), сокращённые свойства объектов, отдельные объявления переменных и скобки условий/циклов. |
| TypeScript     | Рекомендуемые правила typescript-eslint, отдельные type imports; в src дополнительно проверяются необработанные Promise и использование Promise вместо синхронного значения. Асинхронные JSX-обработчики допустимы.                                    |
| React/JSX      | Рекомендуемый TypeScript-профиль ESLint React, ключи списков, вложенные компоненты, корректные DOM-свойства, явный тип кнопок, лишние fragments, самозакрывающиеся пустые элементы и лишние строковые выражения JSX.                                   |
| Hooks          | Правила вызова hooks и полнота зависимостей от официального eslint-plugin-react-hooks. Одноимённые проверки другого React-плагина отключены, чтобы не дублировать диагностику.                                                                         |
| Доступность    | Рекомендуемый профиль JSX a11y: alt, ARIA, подписи контролов, ссылки и клавиатурные взаимодействия. Это статическая проверка, не сертификация доступности.                                                                                             |
| Импорты        | Существование модулей, отсутствие дублей, импорты в начале файла, группы Node/внешние/локальные/type с пустыми строками, алфавитный порядок модулей и именованных импортов.                                                                            |
| Читаемость     | Пустые строки после импортов, перед return/объявлениями функций и типов, между блоками логики и методами классов. Не вводятся лимиты длины функций и обязательные префиксы имён refs.                                                                  |
| Форматирование | Prettier: единые отступы, кавычки, переносы, ширина строки, запятые и оформление JSX/CSS/Markdown. EditorConfig задаёт UTF-8, LF, два пробела и финальный перевод строки; .gitattributes сохраняет LF при Git checkout на Windows.                     |

В конфиге есть два локальных уточнения правил доступности: именованная область прокрутки сообщений получает клавиатурный фокус, а форма нового чата обрабатывает Escape от вложенных контролов. Они не превращаются в кнопки; проверки мыши и прочих элементов остаются включены.

Команды:

- `npm run check` — линтер, форматирование, unit-тесты и сборка.
- `npm run fix` — автоисправления ESLint, затем Prettier.
- `npm run lint` / `npm run lint:fix` — проверка / автоисправления кода.
- `npm run format` / `npm run format:check` — форматирование / проверка Prettier.
- `npm run test:e2e` и `npm run test:e2e:production` — отдельные браузерные прогоны.

Приватные каталоги и генерируемые файлы исключены из команд качества. TypeScript закреплён на 6.0.3: typescript-eslint 8.72.0 объявляет поддержку TypeScript >=4.8.4 <6.1.0.

Основания: [наборы typescript-eslint](https://typescript-eslint.io/users/configs/), [ESLint React](https://github.com/Rel1cx/eslint-react), [React Hooks](https://react.dev/reference/eslint-plugin-react-hooks), [правила импортов](https://github.com/un-ts/eslint-plugin-import-x), [JSX a11y](https://github.com/es-tooling/eslint-plugin-jsx-a11y-x), [совместимость с Prettier](https://prettier.io/docs/integrating-with-linters).
